# Unread

macOS menu-bar app that reads on-screen text aloud with an on-device natural voice. Point at a paragraph, hold ⌃, listen. Free, open source, personal tool first.

**Read [`docs/design.md`](docs/design.md) before making product or architecture decisions.** It holds the research, the interaction design and its reasoning, technical findings, measurements and the prioritized next steps.

## Non-negotiables

- **Effortless is the product.** The user never selects text. Every feature should reduce effort, not add a step.
- **Hotkey is ⌃ Control.** The author runs Hex (voice dictation) on ⌥ Option, so never use Option.
- **Local-first.** On-device TTS by default. Cloud voices could be an optional bring-your-own-key extra, never the default.
- **Fast feel, the Hex playbook:** models stay warm, work starts on key-down, synthesis runs ahead of playback. Measure latency; don't guess.
- **Languages:** English first, French second, others later.

## Build, run, test

```bash
scripts/build.sh                      # release build; Swift 6.2 toolchain; macOS 15+, Apple Silicon. Not a bare `swift build` (see below)
./.build/release/Unread               # menu-bar app; needs Accessibility permission
./.build/release/Unread --bench       # silent: model load + synthesis timings
./.build/release/Unread --bench --split  # silent: also synthesis vs length, and splitting long first sentences (#14): time, join pause, pitch, word timing
./.build/release/Unread --extract     # print sentences + bounds Unread would read from the front window
./.build/release/Unread --simulate x,y [seconds] [--pid N] [--speed X] [--record out.wav] [--voice narrator] [--primed [S]] [--speed-change-at T] [--voice-change-at T] [--jump-at T]  # muted reading from a point (draws the highlight); --record writes what the player outputs, pauses included; --primed starts from a hold released S s (0.4) after speculation began; --jump-at holds to jump back to the start
./.build/release/Unread --stretch-check  # silent: the narrator's time stretch at every menu speed (scripts/test.sh runs it)
./.build/release/Unread --stats       # p50/p95 latency from ~/Library/Logs/Unread/latency.jsonl
./.build/release/Unread --words ["sentence"]  # silent: when each word starts, as the voice times it
./.build/release/Unread --narrate ["sentence" …] [--voice id] [--out f.wav] [--runs N] [--cancel-test] [--long-test] [--switch-test [--cold]]  # silent: the narrator voice: load, first audio, speed, stalls, pitch, GPU time; --voice reads its language in that preset; --switch-test switches through every preset (--cold: clip encoded afresh)
./.build/release/Unread --settings-snapshot out.png [seconds] [--tab voices|highlight] [--dark]  # render the Settings window off-screen (no screen recording needed)
./.build/release/Unread --highlight-frames out.png|out.gif [from] [to] [--style mark=tail,motion=flow] [--zoom x,y,w,h]  # the demo frame by frame, to review motion
```

```bash
scripts/bundle.sh [--install]         # signed Unread.app in build/ (--install: copy to ~/Applications and restart it); logs: ~/Library/Logs/Unread/unread.log
```

- The bundle is signed with the first "Apple Development" identity so the Accessibility grant survives rebuilds. Dev modes work from the bundle too: `build/Unread.app/Contents/MacOS/Unread --extract`.

- The first clean build compiles FluidAudio (2–15 min depending on cache). After that, rebuilds take seconds.
- Never copy `.build` between folders: Swift's precompiled headers bake in absolute paths and the build fails.
- The first launch of a new binary spends ~13 s preparing the CoreML models. After that, load is ~0.8 s.
- Models (~360 MB) are cached in `~/.cache/fluidaudio`.
- The narrator's model set (2.88 GB) is fetched by `scripts/fetch-narrator.sh` (pinned revision, sha256 per file, resumable; `--from DIR` copies matching files from a local copy) into `~/Library/Application Support/Unread/models/Qwen3-TTS-1.7B-Base-ANE`. It isn't bundled. Without it, `Narrator.load` throws an error that names the script.
- **Build with `scripts/build.sh`, never a bare `swift build -c release`.** SwiftPM 6.2 emits FluidAudio's trait defines in random Set order, so a bare build can recompile FluidAudio (~60 s) with nothing changed, and costs the next scripted build the same. The script sets `SWIFT_DETERMINISTIC_HASHING=1`.
- `scripts/test.sh` builds, then checks every fixture page in both web engines (WebKit and Electron windows that are invisible and click-through), and `.txt`/`.rtf` pages in a native text view, against its `<page>.expected.txt`, all in parallel: ~20 s, then ~10 s scoring the local corpus if one is saved; ~5 s with `--quick` (skips `rerender.html`, which pauses 1.6 s per sentence). Run it before and after any change to `Document.swift`. One page with full output: `scripts/extract-fixture.sh fixtures/pages/<page>.html`. See `fixtures/README.md`.
- `scripts/make-voices.sh` makes the narrator's voice presets (#60) from `scripts/voices/voices.json` (descriptions, reference sentences, preview text): VoiceDesign says each reference sentence several times, Whisper checks every take against its transcript, the best is installed in `Resources/Voices`, the app's own narrator reads the preview, Whisper checks that too, and it's stored as AAC. Each step skips what's made, so a new voice is one entry and a rerun. Its venv (`build/voices/.venv`) is made from the pinned `scripts/voices/requirements.txt` with uv. VoiceDesign and Whisper use the GPU (~7 GB), at utility priority, one model at a time. `scripts/make-voices.sh report` lists every candidate and why it was rejected; `audition DIR` copies the previews out with readable names.
- `scripts/score-corpus.sh` scores real pages (Anthropic, OpenAI, Cloudflare, Simon Willison, Dan Luu, Wikipedia) in both engines: sentence precision, recall and bounds per page, against a recorded baseline. The snapshots hold third-party text, so they're local only (`fixtures/corpus/`, gitignored); only the manifest `fixtures/corpus.txt` is committed, and `scripts/save-corpus.sh` saves them. `scripts/test.sh` prints the table; a fresh clone has none. Run it before and after an extraction change.
- `--extract` and `--bench` are the safe ways to verify changes without hijacking the user's keyboard or playing audio. Ask before launching the full app or playing sound on the user's machine.

## Code map

`Sources/Unread/`: `Hotkey` (⌃ hold/tap/double-tap, chord cancel) · `AX` (Accessibility helpers, `AXWorker` queue) · `Document` (find text under the pointer, walk sentences) · `Session` (synthesis pipeline, playback queue, highlight following, opening-clause split) · `Audio` (Kokoro EN v3 + FR legacy, language detection, AVAudioEngine) · `Highlight` (highlight style settings, word-mark logic, the layer renderer shared by the overlay and the Settings demo) · `Overlay` (click-through panels, one per screen) · `Settings` (Settings window: narrator voices, and the highlight with a live demo) · `Voices` (voice presets in `Resources/Voices`, the chosen one per language, preview playback) · `Narrator` (Qwen3-TTS 1.7B on the Neural Engine cloning a preset per language, switchable between sentences, streaming one sentence at a time; chosen in the menu's Voice submenu) · `Take` (a piece's audio: Kokoro's whole, the narrator's as it streams; estimated word starts) · `Stretch` (pitch-preserving time stretch for the narrator's speed) · `NarratorBench` (`--narrate`) · `Words` (word timing from Kokoro durations, word boxes) · `Latency` (per-reading timing log + `--stats`) · `Bench` (`--bench --split`) · `App` (menu bar, interaction state machine) · `main` (entry point + dev modes). `Vendor/QwenANE`: Gloam Voice Studio's Core ML runtime for Qwen3-TTS, vendored (MIT); its README lists what was taken and Unread's changes.

## Hard-won constraints (details in docs/design.md)

- **Chromium/Electron AX is a subset of WebKit's.** These fail in Chromium:
  - `AXTextMarkerForPosition`
  - `AXStartTextMarkerForBounds`
  - `AXNextSentenceEndTextMarkerForTextMarker`

  These work in both engines:
  - element hit-testing + `AXTextMarkerRangeForUIElement`
  - paragraph ranges and word/char stepping
  - `AXStringForTextMarkerRange` and `AXBoundsForTextMarkerRange`

  `WebDocument` deliberately uses only this common subset. Keep it that way.
- Chromium reports each **wrapped line** as a paragraph and joins blocks with **no separator**. That's why sentences are cut from a ~600-character window and block breaks are detected via a shared ancestor.
- Chromium sometimes returns viewport-sized bounds. Treat those as "no bounds".
- **Markers must be anchored to a text leaf (`AXStaticText`).** A marker taken from a container's range (the web area, a hit-tested message block) keeps that anchor through every navigation call, and Chromium then answers every bounds query with the container's box. Hit-test results are resolved down to the leaf under the point (`WebDocument.textLeaf`).
- **Chromium measures a range precisely only if both ends are inside a leaf.** Sentence bounds are therefore the union of per-word boxes, dropping words that come back taller or wider than a word can be and re-measuring those from a few characters in.
- **Chromium's hit test is unreliable** (in T3 Code it can return a 1 px button that doesn't contain the point). Use a hit only if it contains the point and holds text; otherwise descend from the web area by frame. Never anchor a marker to a container.
- **Chromium can switch its tree off again** (auto-disable), leaving the focused "window" as an `AXApplication` stub. `AXManualAccessibility` always reads back false, so `AX.enableTree` judges by tree health: on first contact it sets the flag only if no `AXWebArea` exists yet (setting it restarts the build), and later re-enables a stub tree at most every 10 s.
- **Highlights are per line** (`ReadableDocument.lines(of:)`), drawn as one shape; a single union box covers the neighbouring sentences.
- **Block breaks come from roles, not hop counts:** static text, links, list markers and `…StyleGroup` subroles (code, strong, emphasis) are inline; anything else is a block. Both engines expose the same structure, except that Chromium shows a `<b>`, `<abbr>` or `<span>` with an id (Wikipedia's) as a plain `AXGroup`: it's inline when it holds only inline content and sits inside an inline element or between inline neighbours (`isInlineGroup`). A `<p>` beside bare text has a block on its other side.
- **Reading scope (#10):** reading stays in the nearest `AXDocumentArticle`, else `AXLandmarkMain`, and skips chrome inside it: nav/banner/footer/complementary landmarks, controls (buttons…), code blocks (WebKit `AXPreformattedStyleGroup`; Chromium a group whose only child is `AXCodeStyleGroup`), figure captions, visually hidden text, timestamps, short link rows (several links and no sentence; a list item that is one link is content, #52). A chrome container the user started in is read. Judge a sentence by the leaf one character *inside* its end (the end marker sits on a boundary), climbing past Chromium's per-line `AXStaticText` boxes. On top, a text layer (#11) measures each sentence's block like a Readability paragraph (`UnitText`: words, link density, sentence punctuation, column), memoized: between the start and the first paragraph only headings, list items and sentences are read, and past it a block that isn't a sentence ends the reading if no paragraph (or prose list) follows in scope.
- **WebKit drops plain `<div>`s from the tree,** so a container's inline children (byline links, tag rows) sit beside its paragraphs and their "block" is the whole article: judge the run of inline siblings between two blocks (`TextUnit`). WebKit also puts rendered `aria-hidden` text in the range string ("Copy linkIntroduction") though no leaf holds it, so a heading speaks its leaves' text.
- **Chromium clips element frames to the nearest scrolling container** (T3 Code's chat, not just the viewport): text out of view comes back full width but 0–1 px tall. Never treat "flat" as hidden; visually hidden text is ~1 px *wide*. Text-marker bounds are not clipped. `fixtures/pages/scroller.html` guards this.
- **Pages rebuild their elements under you** (T3 Code re-renders messages while an agent works). Stale markers read as `""`. `WebDocument.relocate` finds the sentence's text in the new tree and rebuilds fresh leaf-anchored markers; `sentence(after:scope:)` uses it to keep walking. `fixtures/pages/rerender.html` guards this.
- **All Accessibility work runs on `AXWorker` (#12), never the main thread.** Documents are confined to that serial queue: create and call them inside `AXWorker.shared.run { }`; the main actor only touches results (sentences, rects). Dev modes in `main.swift` may call documents directly because they're single-threaded. `--simulate` prints a main-thread stall meter.
- **The player gets one sentence at a time (#15):** a buffer on `AVAudioPlayerNode` can't be taken back. The next sentence is scheduled when the current one's speech is *consumed* (its closing pause, never under 120 ms, gives the slack for gapless playback); synthesized audio waits in the session, numbered, so a speed or voice change can redo it. `--simulate … --speed-change-at T` exercises this.
- **WebKit exposes embedded objects as U+FFFC ("￼")** (icon buttons, images) and its character step **stalls at them**, one object at a time. Treat "￼" as blank when tokenizing and measuring, step past objects with `step(past:)` (falls back to the next text leaf in document order), and never let `walk` jump to the window's end. `fixtures/pages/icons.html` guards this (modelled on raphaelsalaja.com, where Safari skipped the first three paragraphs).
- **Chromium browsers may give no text positions** (Aside; likely Chrome/Arc/Dia unless VoiceOver is on). `AXManualAccessibility` is Electron-only (browsers answer −25205, unsupported); their tree is built without inline text boxes, so every text-range bounds query returns a zero-size box while element frames are right. `WebDocument.probeTextGeometry` detects this once per page and highlights whole text blocks instead (`elementFrames`). Only `AXEnhancedUserInterface` would turn on inline text boxes, and it's banned below; see the open decision in docs/design.md.
- **A "next" marker can lie behind the one you asked from.** From the empty line between two `<br>`s, WebKit's `AXNextTextMarkerForTextMarker` returns the start of the paragraph before them. `AXTextMarkerRangeForUnorderedTextMarkers` hides this, so `step(past:)` rejects a step whose ordered range starts at the new marker (`isAfter`). Same in Chromium tables: the next leaf in tree order after the last cell is the first cell again (`AXColumn` lists the cells). `fixtures/pages/breaks.html` and `flow.html` guard this.
- **Chromium's range string drops the space at a line wrap between two elements** ("sevenevery") though the leaves' `AXValue` keep it, and its "paragraphs" can be single text runs. `chunk` records where a space was lost (the spoken text puts it back) and grows past 12 paragraphs while its first sentence is unfinished.
- Enable Chromium's tree with `AXManualAccessibility` only. Never set `AXEnhancedUserInterface`: it breaks window animations.
- **Word highlight (#20) needs two alignments.** The voice's words aren't the page's: acronyms are spelled out ("API" → 3 words), French merges phrases ("tout le monde" → 1), numbers expand ("$45.99" → 5). Kokoro token id 0 is BOS/EOS and 16 is the space in both vocabularies. Match `normalizedText` to spoken words by length, then display words to `normalizedText` by spelling (`WordTiming`). Check with `--words`.
- **The mark follows `AVAudioPlayerNode`'s timeline, not a timer.** That timeline keeps running when the node runs dry, reports nil while paused, and restarts at 0 on `stop`; `Player.claim` accounts for all three. Subtract the output's presentation latency (Bluetooth). The mark is a pure function of that position (`WordMark.frame`), drawn every display frame; don't hand its motion to Core Animation's implicit animations.
- **Native text views scroll by setting `AXVisibleCharacterRange` (#13)**, which leaves the selection, caret and focus alone. Never move the caret to scroll. `AXScrollToVisible` and page-scroll actions are unsupported on NSTextView. Native positions are `NativeRange`s tagged with a text version, so ranges survive edits made while reading.
- **A long first sentence is said in two pieces (#14):** its opening clause (4–14 words, ending at a comma, semicolon, colon or dash) and the rest, when the rest is 60+ characters. Kokoro doesn't stream and takes ~40 ms + 1.45 ms per character, so first audio waits for the opening only. Only a reading's first sentence is split; later ones are synthesized while earlier ones play. The pieces are one sentence to the highlight and the word mark, and only the last gets the closing pause.
- **Kokoro pads every chunk with ~0.3 s of quiet before the voice and ~0.5 s after.** Joined as is, two pieces have a ~0.8 s hole. **A clause synthesized alone ends falling, like a sentence** (French "lire," 177→137 Hz where the whole sentence rises to 240 Hz). So the opening is synthesized with the next 3 words and cut at the pause the voice makes there (`Speech.cut`), and the rest's lead-in is trimmed. Check with `--bench --split`.
- **Pauses are Unread's, not the voice's (#56).** Each piece's own lead-in and tail quiet is trimmed to 50 ms, and `Pacing` puts 0.5 s between sentences and 1.0 s after a paragraph, heading or list item (`Sentence.endsBlock`), divided by the speed. `--extract --blocks` marks block ends with " ¶".
- **The narrator (#62) runs on the Neural Engine through Core ML, in-process, with the GPU unused** (`--narrate` reads the GPU driver's registry: 0 clients, 0 ms). Its quirks:
  - **Core ML compiles the models per binary path.** The first load from a new path (`.build/release/Unread`, `build/Unread.app`, a copy) takes ~50 s; after that ~1.4 s. Rebuilding in place doesn't recompile.
  - **The model starts most sentences with 0.1–0.6 s of quiet,** generated at ~52 ms a frame like speech. The stream starts 50 ms before the voice (`QwenStreamTrimmer`), and the chunk size stays at its first, short value until then (`speechStarted`), so the quiet costs its generation time and no more.
  - **The vocoder's upsampler runs on the CPU.** On the Neural Engine each call queues behind the talker (85–130 ms instead of 27), so first audio is ~100 ms later and short chunks are expensive.
  - **Chunks grow slowly and stay small** (`Narrator.chunkFrames`, 2, 2, 3, 4 frames, then 4). Synthesis runs at ~0.7× real time, and the chunk with the voice's onset can hold under 100 ms of audio, so a chunk that grows faster than playback leaves the player waiting (`[2, 4, 8, 12]` did in every sentence). Bigger chunks also arrive in bursts (a 12-frame one takes ~650 ms), which a player reading sped up can't ride out; capping at 4 costs no speed.
  - **The talker's memory is a fixed 1024 slots** shared by the prompt (the clip's ~73 frames, both transcripts) and the generated frames (12.5 a second). A sentence that doesn't fit at 1.5 frames a character is said in clause-sized parts (`QwenReadRules.split`, 200 characters) through one `QwenTalkSession`, which carries each part into the next. Unsplit, the audio would stop mid-sentence (`contextFull`).
  - Seeds are per sentence (`QwenTalkSession.stableSeed`), so a sentence always sounds the same, quiet start included.
- **Reading with the narrator (#62): only the piece playing streams.** A narrator take (`NarratorTake`) is queued as soon as it's asked for and fills in as it streams. If it's still incomplete when its turn comes (a reading's first sentence, and the next one or two, before synthesis gets ahead), it goes *live* (`ReadingSession.live`) once `Narrator.prebuffer` has arrived: each chunk is handed to the player as it comes, and nothing else is scheduled until the last one is. Takes waiting behind it stay off the player, raw, so #15 holds. A chunk that lands after the player ran dry starts later on its timeline; `Live.runs` records where each run landed so the word starts follow. Only Kokoro splits the opening clause (#14): the narrator's first audible chunk takes as long for 31 characters as for 194.
- **The narrator says one sentence at a time, so a hold must get it first.** When a hold starts a narrator speculation, the reading yields (`yieldNarrator`): it stops the sentence it's synthesizing ahead and starts no new one until aiming ends, so the speculation isn't queued behind it (`--jump-at`: first audio after the jump 218 ms instead of a cold ~600). A sentence still streaming into the player can't be stopped without cutting it, so a jump early in a reading gets no head start. A dropped speculation stops its own stream (`Speculation.deinit`), and a release that jumps stops the old reading before aiming ends, so it can't refill the narrator first.
- **The narrator has no speed control, so its speed is a time stretch** (`TimeStretch`, WSOLA, on the raw audio as it's played). Speed changes don't redo narrator audio, only Kokoro's. The output depends only on the input, not on how it was chunked. `AVAudioUnitTimePitch` was rejected: offline, it glitched at chunk joins unless kept ~8k samples behind the input (~0.3 s more first audio); in the graph, it would stretch `Pacing`'s pauses again and move the word mark's clock off the player's timeline.
- **The narrator times no words until #58.** `WordTiming.estimated` spreads them by characters over the voiced span (its end predicted at the preset's `pace` while the take streams). It's a stopgap; the sentence highlight is unaffected.
- **Voice presets (#60) are data:** `Resources/Voices/<id>.json` (name, language, summary, description, transcript, preview, pace), the clip the Base model clones (`<id>.wav`, mono 24 kHz PCM16: the clip encoder refuses other formats) and a preview (`<id>-preview.m4a`) the narrator recorded, so Settings plays it with no synthesis. **The transcript must be exactly what the clip says,** or the clone garbles: `make-voices.sh` keeps only takes Whisper hears word for word. **A clone keeps its clip's tempo,** so descriptions ask for a natural, steady pace and takes outside 13–19 voiced c/s are dropped. VoiceDesign often makes a "man" at 180–270 Hz; takes on the wrong side of 175/150 Hz are dropped.
- **The narrator reads each language in that language's preset** (`NarratorVoices`; French falls back to the English voice if it has none). `Narrator.use` switches between sentences on the narrator's own queue, so the sentence in flight finishes in the old voice; it costs ~330 ms of warming (prompt rows, talker memory prefix, vocoder priming), and the encoded clip is cached on disk after its first ~1 s. Then the session redoes that language's queued narrator takes (`narratorVoiceChanged`). Each take carries its voice's `pace` for the prebuffer and the word estimate.
- Kokoro v3 (fast ANE path) supports English, Japanese and Mandarin only. French uses the legacy pipeline with a single voice, `ff_siwis`.
